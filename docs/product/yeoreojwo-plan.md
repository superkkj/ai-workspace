- 기획일: 2026-11-18 (Asia/Seoul)
- 사용자 결정: 후보 ②, 원하는 활동을 먼저 모으고 공방·강사가 제안하는 플랫폼을 개발한다.
- 문서 상태: 구현을 위한 기준. 이 문서에서는 기능 구현·테스트를 완료로 선언하지 않는다. 아래 검사는 미실행 계획이며, 실제 완료 여부와 실행 결과는 [STATUS.md](../../STATUS.md)와 [CHECKS.md](../ai/CHECKS.md)에 별도로 기록한다.
- 작업 원칙: [AGENTS.md](../../AGENTS.md), [개발 흐름](../ai/WORKFLOW.md), [확인된 해결 기록](../../LESSONS.md)을 적용한다.
- 코드 위치 계획: `apps/yeoreojwo/`. 초기 기술 선택은 React·TypeScript·Vinext와 영속 데이터 저장소 D1이며, 실제 설치·실행 결과를 별도 기록한다.

## 1. 해결할 일

**원하는 활동의 시간·동네·예산이 맞지 않아 신청하지 못한 사람이, 같은 조건의 사람들과 수요를 모아 실제 운영자의 제안을 받고 참가를 확정하는 도구.**

첫 사용자는 한 생활권에서 공예·베이킹·취미 입문 수업을 찾는 성인과 소규모 공방·강사다. 먼저 참여자를 확보한 지역에서 운영을 검증하되, 코드에서 특정 학교·행사·동네만 사용할 수 있도록 고정하지 않는다.

### 설명용 사용 장면

1. 참가자 A가 “평일 저녁에 초보 도자기 수업을 열어주세요”라는 요청에 동네·희망 시간·1인 예산·희망 인원을 작성한다.
2. B와 C가 “관심 있어요”로 참여한다. 이 행동은 예약이나 결제가 아니다.
3. 공방 D가 실제 날짜·소요 시간·장소·가격·최소 참가 인원·정원·준비물을 제안한다.
4. A가 제안을 선택하면 관심 참여자들은 확정된 조건을 읽고 각자 참가 여부를 결정한다.
5. 시작 시각에 소요 시간을 더한 종료 시각이 지나고 확정 인원이 최소 참가 인원 이상일 때 진행 완료를 기록한다. 취소됐다면 성사 건수로 세지 않는다.

이는 가상 예시다. 실제 참가자나 공급자에게 연락하거나 수업을 성사시킨 상태로 기록하지 않는다.

## 2. 첫 버전의 핵심 기능 세 가지

| 묶음 | 사용자 행동 | 완료 결과 |
| --- | --- | --- |
| 활동 요청과 관심 참여 | 요청 작성, 목록·상세 조회, 지역·분야 검색, 관심 참여·취소 | 같은 조건의 수요와 요청 내용을 확인한다. |
| 운영자 제안과 선택 | 공방·강사가 조건을 제안, 요청자가 비교 후 하나를 선택 | 참가자가 판단할 정확한 일정·가격·장소·정원이 정해진다. |
| 참가 확정과 진행 결과 | 선택된 조건에 참가 확정·취소, 모임 종료 후 완료 또는 취소 기록 | 관심 숫자와 실제 확정 인원을 구분하고 결과를 남긴다. |

요청 작성·관심 참여·제안·선택·확정·종료의 결과가 새로고침 후에도 유지돼야 한다. 목록 화면의 버튼만 바뀌는 시연으로 완료 처리하지 않는다.

### 이번 범위에서 제외할 기능

- 결제·정산·환불 처리, 수수료 청구, 자동 예약 대행.
- 실시간 채팅, 문자·이메일 발송, 외부 플랫폼 자동 수집.
- 지도 API, 이미지·신분증·사업자 증명 파일 업로드, 정교한 추천 AI.
- 사업자 진위 보증, 후기 신뢰 점수, 자동 안전 인증 표시.
- 동반인 여러 명을 한 계정으로 예약, 대기 순번, 반복 일정, 여러 제안 동시 개설.
- 기존 요청·제안의 내용 수정. 요청은 취소 후 새로 작성하고, 선택되지 않은 제안은 철회 후 새로 작성한다.

초기 버전의 “참가 확정”은 이 서비스 안에서 의사를 기록하는 기능이다. 결제 완료 또는 외부 예약 완료라고 표시하지 않는다. 외부 예약 링크를 제공하는 경우에도 그 방문 결과를 결제·예약 완료로 추정하지 않는다.

## 3. 정보와 역할

### 최소 입력

| 대상 | 필요한 값 | 첫 버전 제한 |
| --- | --- | --- |
| 사용자 | 서버에서 확인한 사용자 식별자, 공개 닉네임 | 원본 인증 식별자와 이메일은 화면·공개 응답에 노출하지 않는다. |
| 활동 요청 | 제목, 설명, 분야, 동네, 희망 요일·시간대, 1인 예산, 희망 인원, 요청 마감 | 필수 입력과 길이·숫자·날짜 범위를 서버에서 확인한다. |
| 관심 참여 | 요청, 사용자, 생성 시각 | 사용자 한 명당 요청 하나에 관심 하나. 작성자는 최초 관심 1명에 포함한다. |
| 운영자 제안 | 요청, 제안자, 운영 이름, 설명, 실제 시작 시각, 소요 분(`durationMinutes`), 장소, 1인 가격, 최소 참가 인원(`minParticipants`), 정원 | 요청과 제안 작성자가 같을 수 없다. 소요 시간은 양수이며 최소 참가 인원은 1 이상 정원 이하로 제한한다. 운영 이름은 자기 기재 정보이며 인증 표시가 아니다. |
| 참가 확정 | 선택된 제안, 사용자, 확정·취소 상태, 변경 시각 | 한 사용자당 한 자리. 선택된 제안의 정원을 넘길 수 없다. |
| 진행 결과 | 요청 상태, 종료 기록자, 변경 시각, 필요 시 짧은 취소 사유 | 완료·취소를 별도로 표시하고 기존 요청을 삭제해 이력을 숨기지 않는다. |

희망 인원은 **수요 목표**다. 참가 확정 수나 운영자가 제안한 최소 참가 인원(`minParticipants`)과 혼동하지 않는다. 제안 정원은 실제 참가 확정의 최대 인원이다. 관심 수가 목표에 도달해도 제안 선택이나 참가 확정은 자동으로 발생하지 않는다. 종료 시각은 시작 시각에 소요 분(`durationMinutes`)을 더해 계산한다.

조회 응답은 공개 프로필과 집계 수 중심으로 구성한다. 공개 목록·상세에 참가자의 이메일, 인증 헤더, 연락처, 원본 사용자 ID를 넣지 않는다. 화면에서 감추는 것만으로 완료 처리하지 않는다.

### 역할과 권한

| 행동 | 허용되는 사람 |
| --- | --- |
| 요청 조회 | 사이트 접근 정책이 허용하는 방문자 |
| 요청 작성·관심 참여 | 서버가 확인한 로그인 사용자 |
| 요청 내용 수정 | 첫 버전에서 제공하지 않는다. 요청 작성자가 취소 후 새 요청으로 작성한다. |
| 운영자 제안 작성 | 요청 작성자와 다른 로그인 사용자 |
| 제안 철회 | 제안 작성자. 선택되지 않은 제안만 철회하고 필요한 경우 새 제안을 작성한다. 내용 수정은 제공하지 않는다. |
| 제안 하나 선택 | 해당 요청 작성자 |
| 참가 확정·개별 취소 | 해당 참가자 본인. 제안자는 자기 수업의 참가자로 집계하지 않는다. |
| 요청 취소 | 요청 작성자. 선택된 제안의 운영자에게도 운영 취소 경로를 둔다. |
| 모임 완료 기록 | 요청 작성자 또는 선택된 제안 작성자. 시작 시각 + 소요 시간이 지난 뒤, 확정 참가 인원이 `minParticipants` 이상인 경우에만 가능하다. |

역할은 화면의 “참가자/운영자 보기” 선택값을 신뢰하지 않고, 서버의 로그인 사용자와 각 기록의 소유자로 판정한다. 테스트용 사용자 전환은 실제 서비스의 인증 경로로 사용하지 않는다.

## 4. 상태와 변경 규칙

### 요청 상태

| 상태 | 의미 | 가능한 주요 행동 |
| --- | --- | --- |
| 모집 중 | 관심과 운영자 제안을 모으는 단계 | 관심 참여·취소, 제안 작성·철회, 요청 취소 |
| 참가 확정 중 | 요청자가 한 제안을 선택하여 조건이 고정됨 | 참가 확정·개별 취소, 모임 취소 |
| 진행 완료 | 선택된 일정의 종료 시각이 지났고 확정 인원이 최소 참가 인원 이상인 모임의 진행 결과를 기록함 | 조회 |
| 취소 | 요청자 또는 선택된 운영자가 진행하지 않기로 기록함 | 조회 |
| 모집 마감 | 제안을 선택하지 못하고 요청 마감 시각이 지남 | 조회. 새 요청을 작성할 수 있다. |

구현에서는 모집 마감을 서버 시각으로 계산해도 된다. 백그라운드 작업이나 사용자의 브라우저 시계가 돌아야만 마감되는 구조로 만들지 않는다.

### 변경 규칙

1. 제안은 요청 마감 전 모집 중일 때만 제출할 수 있다. 과거 일정, 음수 가격, 양수가 아닌 소요 시간, 잘못된 정원, 최소 참가 인원이 1 미만이거나 정원을 넘는 값은 거절한다.
2. 요청 작성자는 마감 전 유효한 제안을 하나만 선택할 수 있다. 이후 다른 제안은 새 참가 확정의 대상이 되지 않는다.
3. 제안 선택 시 관심 참여자를 자동 확정하지 않는다. 요청 작성자도 참가하려면 확정된 조건을 확인하고 참가한다.
4. 같은 사용자의 연속 클릭·재시도 때문에 관심·확정 숫자가 중복 증가하지 않아야 한다.
5. 마지막 한 자리에 두 사용자가 동시에 참가를 요청해도 한 명만 확정돼야 한다. 정원 검사는 원자적인 DB 변경과 함께 수행한다.
6. 참가 취소는 시작 전까지 허용하고 해당 자리를 돌려준다. 다시 참가할 때도 남은 자리와 상태를 검사한다.
7. 시작 시각이 지난 제안에는 새 참가 확정이나 개별 취소를 허용하지 않는다. 종료 후 결과 기록과는 구분한다.
8. 첫 버전은 요청·제안 내용 수정 기능을 제공하지 않는다. 요청은 취소 후 재작성하고, 선택 전 제안은 철회 후 재작성한다. 선택된 제안의 날짜·소요 시간·가격·장소·최소 참가 인원·정원을 바꿔 기존 동의를 다른 조건에 재사용하지 않는다. 선택 이후 조건을 바꾸려면 모임을 취소하고 새 요청으로 다시 모집한다.
9. 모임 취소 후 관심·제안 선택·참가 확정·완료 처리는 모두 거절한다. 이미 확정했던 정보는 취소 결과와 함께 남긴다.
10. 완료는 선택된 제안이 있고, 서버 시각이 시작 시각 + `durationMinutes`로 계산한 종료 시각 이후이며, 취소되지 않은 확정 참가 인원이 `minParticipants` 이상일 때만 가능하다. 시작 직후, 최소 인원 미달, 권한 없는 사용자의 완료 요청은 거절한다.
11. 공개 모집 수·확정 수·완료 수는 예시 데이터와 실제 데이터를 구분한다. 관심 목표 달성이나 운영자의 제안을 “모임 성사”로 표현하지 않는다.

DB에는 시각을 명확한 기준으로 저장하고 사용자에게 한국 시간으로 표시한다. 날짜 입력, 마감 판정, 테스트에서 기준을 통일한다.

## 5. 화면 구성과 문구

- **활동 찾기:** 지역·분야 검색, 요청 카드, 명확한 상태, 관심 인원, 예산·희망 시간, 요청 작성 버튼.
- **요청 작성:** 필수 항목을 짧게 묻고 실패한 입력 옆에 원인을 표시한다. 성공하면 저장된 요청의 상세로 이동한다.
- **요청 상세:** 요청 조건, 관심 참여, 운영자 제안 목록, 선택된 조건, 내 참가 상태와 가능한 다음 행동.
- **내 활동:** 내가 올린 요청, 관심 있는 요청, 제출한 제안, 확정한 일정. 비어 있으면 무엇을 할 수 있는지 안내한다.

“관심 있어요”와 “이 조건으로 참가할게요”를 다른 행동으로 보여준다. 제안 선택을 “결제 완료”나 “참가자 전원 확정”으로 설명하지 않는다. 저장 중 연속 클릭 방지, 저장 실패 안내, 새로고침 후 상태 복원, 검색 결과가 없는 경우를 포함한다.

모바일 좁은 화면에서 가로 스크롤이 생기지 않고, 폼의 라벨·오류·키보드 포커스가 보여야 한다. 다이얼로그를 사용하면 닫기와 키보드 이동이 가능해야 한다.

## 6. 샘플과 개인정보

초기 화면을 이해하는 데 필요한 예시 요청을 제공할 수 있다. 아래 조건을 모두 지킨다.

- 모든 예시 카드와 상세에서 “예시” 표시를 유지한다. 가상 참가자와 가상 공방을 실제 이용자·업체로 소개하지 않는다.
- 예시 데이터가 실제 모집 중인 요청과 혼동되지 않게 목록·상세·집계를 구분한다.
- 예시에는 실존 개인의 이름·연락처·사진·정확한 사적 주소를 쓰지 않는다.
- 실제 사용자가 입력한 내용은 데이터 저장소에 보관하고 공개 GitHub 커밋에 포함하지 않는다.
- 로그인 관련 값, 토큰, 환경변수, 로컬 DB, 브라우저 테스트의 인증 자료를 커밋하지 않는다.
- 처음부터 영수증·사업자 증명·신분증·직접 연락처를 수집하지 않는다. 공개 글에 민감한 정보를 쓰지 않도록 입력 안내를 제공한다.

공개 GitHub 저장소와 앱의 방문 가능 범위는 별개다. 앱이 소유자에게만 공개된 검증 환경이라면 이를 실제 상태에 정확히 기록한다. 공유 범위를 넓혔다고 확인하지 않은 상태에서 누구나 가입할 수 있다고 안내하지 않는다.

### 자동 검사로 확인할 것

| 시나리오 | 만족해야 할 결과 |
| --- | --- |
| 올바른 요청 작성 | 영속 저장되며 재조회에서 작성 내용과 소유자가 일치한다. |
| 입력 검증 | 필수 항목 누락·초과 길이·잘못된 숫자·과거 마감/일정·양수가 아닌 소요 시간·정원을 초과한 최소 참가 인원을 서버가 거절한다. |
| 관심 참여 재시도 | 같은 사용자가 여러 번 요청해도 수가 중복 증가하지 않는다. |
| 제안과 선택 권한 | 다른 사람의 제안을 철회하거나 다른 사람 요청의 제안을 선택할 수 없다. 본인 요청에 제안할 수 없고, 내용 수정 경로를 제공하지 않는다. |
| 관심과 확정 분리 | 제안 선택 후 확정 수는 자동으로 관심 수가 되지 않는다. |
| 참가 확정과 취소 | 본인의 상태만 바꾸고, 취소한 자리가 다시 사용 가능해진다. |
| 동시성 | 마지막 자리에 동시 신청해도 정원 초과가 발생하지 않는다. |
| 마감과 취소 | 마감·시작 이후 또는 취소 상태에서 금지된 변경을 서버가 거절한다. |
| 완료 처리 | 선택된 제안·시작+소요 시간 이후·확정자 수가 최소 참가 인원 이상·요청 작성자 또는 선택된 운영자라는 조건을 모두 확인한다. 시작 직후와 최소 인원 미달에는 거절해야 한다. |
| 데이터 경계 | 조회 응답에 이메일·원본 인증 식별자·토큰이 포함되지 않는다. |

반복 요청을 현재 상태로 반환하거나 명확한 충돌 응답으로 처리할 수 있지만, 중복 데이터나 잘못된 집계는 남기지 않는다.

### 실제 화면에서 확인할 것

1. 서로 다른 역할의 검증용 사용자로 요청 작성 → 관심 참여 → 제안 작성 → 제안 선택 → 참가 확정을 끝까지 수행한다.
2. 중간에 페이지를 새로고침하고 목록·상세·내 활동의 숫자와 상태가 일치하는지 확인한다.
3. 참가 취소 후 정원, 요청 취소 후 가능한 버튼, 입력 실패 시 오류 안내를 확인한다.
4. 넓은 화면과 휴대폰 폭에서 목록·입력·상세를 확인하고 주요 버튼과 폼을 키보드로 이용한다.
5. 빈 목록·검색 결과 없음·데이터 요청 실패가 흰 화면이나 성공 안내로 처리되지 않는지 확인한다.

브라우저 환경, 로그인 역할, 영속 저장소 또는 배포 확인이 불가능하면 그 항목을 미실행으로 남긴다. 빌드 성공을 전체 사용 흐름 통과로 대체하지 않는다. 실제 유료 수업, 외부 예약·결제, 일반 이용자의 참여 수요는 이 개발 테스트의 검증 범위가 아니다.

## 8. 초기 운영과 제품 가설

현재 확인할 가장 큰 가정은 **관심을 표시한 사람이 정확한 날짜·가격·장소가 나온 뒤 실제로 참가를 확정하는가**다. 전체 회원 수보다 한 생활권·시간대·활동에 겹치는 수요가 중요하다.

개발 이후 제안하는 소규모 실험은 한 생활권의 공방·강사 3~5곳과 실제 요청 10건 안팎을 대상으로 요청→제안→확정→진행을 수작업으로 지원하는 것이다. 이는 모집·성과 예측이 아니며 아직 수행하지 않았다. 커뮤니티나 공급자에게 실제 연락할 때는 별도의 사용자 지시가 있어야 한다.

- 계속할 근거: 구체적인 제안에 참가가 확정되고 실제 활동이 진행되며, 일부가 다음 요청을 다시 남긴다.
- 수정할 근거: 관심은 모이지만 가격·시간이 공개되면 대부분 이탈한다. 요청에서 받아야 할 조건과 참여 확인 방식을 고친다.
- 보류할 근거: 운영자가 매번 모든 조건을 대신 조율해야 하거나, 기존 단체방·예약 서비스로 같은 일이 더 쉽게 해결된다.

초기 운영 부담은 운영자 확인, 무관한 홍보, 노쇼·일정 변경, 취소 문의다. 데이터와 이용 사례가 생긴 뒤 필요한 신고·운영 정책과 지원 절차를 보완한다. 첫 버전만으로 일반 공개 상용 서비스 운영이 모두 준비됐다고 평가하지 않는다.

## 9. 확장 순서

1. **이번 개발:** 직접 입력 기반의 요청·관심·제안·확정·결과 흐름과 영속 저장, 권한 검사, 핵심 검증.
2. **실사용 확인 후:** 다른 생활권과 인접 활동으로 확대하고 신고·운영 도구, 알림, 참가자 연락 수단을 필요한 범위에서 추가한다.
3. **반복 거래 확인 후:** 예약·결제·정산·환불과 공급자 자격 확인을 별도 프로젝트 범위로 설계한다.

공예에서 베이킹·입문 강습·소규모 팀 체험으로 대상이 바뀌어도 요청 조건·관심·제안·확정이라는 핵심 구조를 재사용한다. 지역별 공급자 모집과 활동별 준비물·인원 조건은 추가 운영 작업으로 따로 평가한다.
