## A. 최신 상태를 확인하는 방법

주기적인 전체 폴링은 추가하지 않는다. 화면 복귀·상세 재진입·사용자 새로고침으로 GET을 수행하고 기존 목록을 유지한다. 같은 상세의 동시 GET은 공유한다. 대상이 바뀌거나 쓰기가 시작되면 이전 요청을 중단하고, 중단을 무시한 늦은 응답도 세대 번호로 폐기한다. 입력 폼의 key는 재조회 시각에 묶지 않는다.

조건 확인을 요청한 뒤 창을 닫은 경우 늦은 조회가 창을 다시 열지 않는다. 제안이 철회된 상태가 반영되면 빈 모달 대신 최신 상세로 돌아가는 안내를 보인다. 모달 안에서 발생한 알림은 native dialog 내부에 표시한다.

## B. 인증 뒤 이어가기

로그인 return_to는 앱 루트와 허용된 query만 구성한다. 외부 URL·//·역슬래시·제어문자·임의 경로는 거절한다. 로그인 링크는 기존 top-level navigation을 사용한다.

관심 작업을 로그인 뒤 자동으로 이어가는 경우에는 같은 탭에서 사용자가 눌렀던 명시적 true/false 의도와 30분 이내의 복귀 키가 일치해야 한다. URL의 resume 값만으로 쓰기 작업을 실행하지 않는다. 저장 공간이 막히거나 다른 탭에서 돌아온 경우에도 같은 상세를 열되 사용자가 관심 버튼을 다시 누른다. 참가 확정은 복귀 키와 관계없이 최신 일정·금액·장소 및 새 동의 체크를 거친다.

## C. 초안과 저장 결과

- 요청·제안·닉네임·취소 사유를 같은 브라우저 탭의 sessionStorage에 보관한다. 서버가 자기 viewer에게만 돌려주는 불투명 draftScope로 계정을 분리한다. 인증 ID·이메일·토큰·동의 체크는 보관하지 않는다.
- 창 닫기·Escape·다시 열기·페이지 새로고침을 지원한다. 다른 기기·다른 탭 동기화나 서버 초안 보관은 하지 않는다.
- 성공 응답을 받거나 사용자가 명시적으로 지우면 해당 초안을 정리한다. 저장 공간이 막히면 현재 페이지 안에서만 유지하고 재접속 보관의 한계를 안내한다.
- 요청 생성의 불명확한 결과는 최초 입력과 operationId를 고정한다. 사용자가 같은 요청의 결과 확인을 누르면 같은 작업만 다시 전송한다. 자동 POST 재시도는 없다.
- requests에 nullable operation_id와 `(owner_id, operation_id)` unique를 추가한다. 기존 데이터는 유지하고 생성 키 없는 기존 API 호출도 호환한다. 키 없는 호출에는 중복 방지를 보장하지 않는다.
- 이미 성공한 작업은 원래 작성 시각 기준으로 재검증하여 마감·취소 후에도 기존 ID를 반환한다. 상태를 되돌리지 않는다. 다른 본문 재사용은 409로 거절한다.
- 입력 거절, 보내기 전 오프라인, 저장 여부 불명, 저장 성공 뒤 조회 실패를 구분한다. 15초 클라이언트 시간 초과를 서버 저장 실패로 해석하지 않는다.

## 검증과 경계

단위·실제 SQL, GitHub CI의 built Worker + 로컬 D1 HTTP, 별도 브라우저 컨텍스트의 합성 사용자 검사를 구분한다. 브라우저의 저장 응답 유실은 실제 POST를 저장시킨 뒤 응답만 끊어 재현한다. 가입·로그인 제공자와 실제 호스팅의 다계정 사용은 별도 검증이다. 최종 실행 결과·실패와 수정·배포 소스는 [CHECKS](../ai/CHECKS.md)에 기록한다.
